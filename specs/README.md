# The shared demo spec

`demo-api.yaml` is the one OpenAPI document every example in this repository
runs against. It describes Parcelio, a fictional multi-carrier shipping API:
shipments, packages, carriers, rate quotes, address validation, pickups,
tracking events, and webhook subscriptions.

It exists so that the tools in this repo can be compared on identical input.
If a generator produces a bad tool name, or a docs renderer hides the OAuth2
scopes, you can see it here rather than in a vendor's hand-picked sample.

## What it covers

| Feature | Where |
|---|---|
| OpenAPI version | 3.1.0 |
| Operations | 29 path operations plus 1 webhook (`shipmentStatusChanged`) |
| API-key auth | Global default, header `X-API-Key`, used by every read operation |
| OAuth2 auth | Authorization-code flow, applied per operation to every write. Scopes: `shipments:read`, `shipments:write`, `tracking:write`, `webhooks:manage` |
| Cursor pagination | Every list operation: `limit` and `cursor` query params, `next_cursor` and `has_more` in the response |
| File upload | `uploadShipmentDocument`, `multipart/form-data` |
| Binary response | `getShipmentLabel`, `application/pdf` or `image/png` |
| Idempotency | `Idempotency-Key` header on `createShipment` |
| Error format | `application/problem+json` (RFC 9457) via shared `components.responses` |
| 3.1 features | `webhooks` top-level object, `type: [string, "null"]`, `const`, `examples` arrays, `contentEncoding` |

Every schema is fully defined. The spec passes `redocly lint` with the
repository's `redocly.yaml` and Spectral's built-in `spectral:oas` ruleset
with warnings only.

## The deliberate defects

Roughly a third of the operations have thin or missing descriptions. This is
intentional and must not be "fixed" in this file. The spec-quality examples
detect these gaps, and the MCP examples show how each generator handles them.

| Defect | Operations |
|---|---|
| No description | `dispatchShipment`, `listPackages` (also no summary), `removePackage`, `tracking_event_ingest`, `cancelPickup`, `testWebhookSubscription` |
| Thin description | `updateShipment` ("Update shipment."), `getPackage` ("Get package."), `getCarrier` ("Returns a carrier."), `getWebhookSubscription` ("Get a webhook.") |
| Inconsistent `operationId` casing | `tracking_event_ingest` (everything else is lowerCamelCase) |

If you want a version with these gaps filled, apply the overlay in
[`examples/spec-quality/agent-readiness/`](../examples/spec-quality/agent-readiness/)
to produce a fixed copy. Do not edit this file.

## Running a backend for it

None of the servers in the spec exist. Every runnable example points at a
mock generated from the spec by Prism. Start it from the repository root:

```bash
npx -y @stoplight/prism-cli@5.16.0 mock -p 4010 specs/demo-api.yaml
```

Prism enforces the security schemes: reads need any `X-API-Key` header, and
writes need any `Authorization: Bearer` header. It validates request bodies
against the schemas and answers from the `examples` in the spec.

```bash
curl -s http://127.0.0.1:4010/carriers                      # 401
curl -s -H 'X-API-Key: demo' http://127.0.0.1:4010/carriers  # 200, example data
```

## Validating it

```bash
npx -y @redocly/cli@2.49.1 lint specs/demo-api.yaml
npx -y @stoplight/spectral-cli@6.16.3 lint -r examples/spec-quality/spectral/.spectral.yaml specs/demo-api.yaml
```

The first command must exit 0. The second reports the deliberate defects as
warnings; see the spectral example for the expected output.

## Changing it

Changes to this file affect every example. Before opening a PR that touches
it, run the CI workflow locally (see `.github/workflows/ci.yml`) and update
any "Expected output" sections that change. Adding operations is fine as
long as the total stays between 25 and 30 and the defect table above stays
accurate.
