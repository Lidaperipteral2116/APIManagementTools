# Redoc (open-source baseline via Redocly CLI `build-docs`)

**What this shows:** Turning `specs/demo-api.yaml` into a single static HTML reference page with the open-source Redoc renderer, driven by Redocly CLI 2.49.1, and what that renderer does with the spec's deliberate rough edges.

Redoc is the reference-only renderer most other tools are measured against: a three-panel layout, no Try It console, no hosting, no account. What it is genuinely best at is producing a predictable, searchable static page from a spec with zero configuration, which makes it the cheapest possible baseline to compare the hosted tools in `../stoplight/` and `../theneo/` against.

Folder layout:

| File | Purpose |
|---|---|
| `redocly.yaml` | Lint rules plus three Redoc rendering options (see Notes for how the option names were verified) |
| `.gitignore` | Keeps `dist/` out of git; it is a build artifact |
| `dist/index.html` | Build output (not committed; regenerate with the command in Steps) |

## Prerequisites

- Node 22 (tested with v22.23.2, npm 10.9.8). No account, no API key.
- Redocly CLI is fetched on demand by `npx`; nothing to install globally.
- A static file server to view the result. The walkthrough uses `serve@14.2.6`.
- Redoc has no Try It console, so it never calls the API. The Prism mock is not needed for this folder. For parity with the sibling folders, the shared mock is started from the repo root with:

  ```sh
  npx -y @stoplight/prism-cli@5.16.0 mock -p 4010 specs/demo-api.yaml
  ```

## Steps

All commands run from the repository root.

1. Lint the spec with the folder config (optional, but it is what CI does first):

   ```sh
   npx -y @redocly/cli@2.49.1 lint specs/demo-api.yaml --config examples/api-docs/redoc/redocly.yaml
   ```

2. Build the HTML page:

   ```sh
   npx -y @redocly/cli@2.49.1 build-docs specs/demo-api.yaml \
     --config examples/api-docs/redoc/redocly.yaml \
     -o examples/api-docs/redoc/dist/index.html
   ```

   `-o` / `--output` is the output path (default `redoc-static.html`). `--config` points at this folder's `redocly.yaml`; without it the CLI picks up the repo-root `redocly.yaml`, which has the same lint rules but no rendering options. Other flags from `build-docs --help`: `--title`, `--disableGoogleFont`, `-t/--template <handlebars file>`, `--templateOptions.<key>`, `--theme.openapi.<option>` (dot notation, same options as the `openapi` block in the config file).

3. Serve and open it:

   ```sh
   npx -y serve@14.2.6 -l 3000 .
   ```

   Open <http://localhost:3000/examples/api-docs/redoc/dist/>. Note that `serve` answers `/dist/index.html` with a 301 to `/dist/`, so use the directory URL. Opening `dist/index.html` straight from disk should also work because the spec is inlined; that path was not exercised in this run.

4. Live preview while editing the spec. Redocly CLI 1.x had `preview-docs`; in 2.49.1 that command is gone (`redocly preview-docs specs/demo-api.yaml` prints the generic command list and exits). The replacement, `redocly preview`, starts the Redocly *project* preview (`--product redoc|revel|reef|realm`, `--plan` defaulting to `enterprise`) which pulls the commercial `@redocly/redoc` package rather than the open-source bundle. For the open-source path, re-run step 2 after each edit, or wrap it in whatever file watcher you already use.

## Keeping docs in sync with the spec

The page is a pure function of the spec at build time. It cannot drift in content, only in time: if nobody rebuilds after a spec change the published page is stale. So the sync mechanism is CI on the spec path.

```yaml
# .github/workflows/redoc-docs.yml
name: Redoc docs
on:
  push:
    branches: [main]
    paths:
      - 'specs/demo-api.yaml'
      - 'examples/api-docs/redoc/redocly.yaml'
  pull_request:
    paths:
      - 'specs/demo-api.yaml'
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - name: Lint
        run: npx -y @redocly/cli@2.49.1 lint specs/demo-api.yaml --config examples/api-docs/redoc/redocly.yaml
      - name: Build
        run: >
          npx -y @redocly/cli@2.49.1 build-docs specs/demo-api.yaml
          --config examples/api-docs/redoc/redocly.yaml
          -o examples/api-docs/redoc/dist/index.html
      - name: Check the page contains every operation summary
        run: |
          for s in "List shipments" "Create a shipment" "Send test event" "Shipment status changed"; do
            grep -q "$s" examples/api-docs/redoc/dist/index.html || { echo "missing: $s"; exit 1; }
          done
      - uses: actions/upload-artifact@v4
        with:
          name: redoc-site
          path: examples/api-docs/redoc/dist/
```

Deploying is out of scope for Redoc itself: hand `dist/` to GitHub Pages (`actions/upload-pages-artifact` + `actions/deploy-pages`), an S3 bucket, or whatever already serves your static files. Pull requests get the same lint plus build, which is where a broken `$ref` or a schema error surfaces before it reaches the published page. Breaking lint on a spec change is the only feedback loop; Redoc has no notion of "the published version" separate from "the file you built".

## Notes

What worked cleanly: lint and build ran first time on the OpenAPI 3.1 document, including `type: [string, 'null']`, `const`, `contentEncoding`, `examples` arrays, and the top-level `webhooks` map. No spec changes were needed and none were made.

What needed hand-editing: only the config. `--config` replaces the repo-root `redocly.yaml` rather than layering on it, so the two lint overrides (`operation-summary: warn`, `no-server-example.com: off`) are duplicated in this folder's file. The rendering options live under a top-level `openapi:` key in Redocly CLI 2.x (the CLI prints `using 'openapi' options` when it finds them). The three options used, `hideDownloadButtons`, `sortRequiredPropsFirst`, `jsonSamplesExpandLevel`, plus `theme.colors.primary.main` and `theme.typography.fontFamily`, were checked two ways: they appear on <https://redocly.com/docs/redoc/config>, and the CLI's config linter (`--lint-config warn`, the default) rejects unknown keys. A deliberate `openapi: { bogusOption: true }` produced `Property \`bogusOption\` is not expected here.` while the real ones passed silently. `hideDownloadButton` (singular) and `jsonSampleExpandLevel` are the deprecated 2.x spellings; the page still loads a Redoc 2.5.3 bundle, so both spellings are accepted today.

How the renderer treats the spec's defects (observed in the built page, 2026-09-01):

- **Missing summary on `listPackages`:** the sidebar entry and the section heading fall back to the operationId, so the Packages group reads `listPackages`, `Add a package to a shipment`, `Get package`, `Remove package`. Nothing in the page flags it; only `redocly lint` does (see Expected output).
- **Missing descriptions** (`dispatchShipment`, `removePackage`, `tracking_event_ingest`, `cancelPickup`, `testWebhookSubscription`): the description paragraph is simply absent; the operation goes straight from heading to `AUTHORIZATIONS:`. **Thin descriptions** (`Update shipment.`, `Get package.`, `Returns a carrier.`, `Get a webhook.`) are printed verbatim. Redoc has no AI or fallback text; what you write is what ships. The `recommended` ruleset does not include an `operation-description` rule, so lint stays quiet about the empty ones too.
- **`info.description` markdown headings** (`## Authentication`, `## Pagination`, `## Idempotency`) become top-level sidebar entries above the tag groups. Useful, and worth knowing before you add a heading to that field.
- **OAuth2 scopes:** each OAuth2 operation shows a collapsed `AUTHORIZATIONS: OAuth2 (shipments:write)` line. Expanded, it renders the scheme description, `Flow type: authorizationCode`, the Authorization, Token, and Refresh URLs, `Required scopes: shipments:write`, and then the full list of all four scopes with their descriptions behind a `See more` link. The global `ApiKeyAuth` shows the same way on read operations.
- **Multipart upload (`uploadShipmentDocument`):** `REQUEST BODY SCHEMA: multipart/form-data` with `file` rendered as `string <binary>`, `type` as an enum chip list, and `description` with its `<= 200 characters` constraint. The `encoding.file.contentType` value (`application/pdf, image/png, image/jpeg`) is not displayed anywhere, so the allowed file types only reach the reader through the prose description.
- **Binary label response (`getShipmentLabel`):** the `200` block has a `RESPONSE SCHEMA` dropdown offering `application/pdf` and `image/png`, each rendered as `string <binary> <application/pdf>`. The right-hand "Response samples" panel only lists `401`, `404`, `409` because Redoc cannot fabricate a sample for a binary body. Nothing is wrong, it just looks as though the success case has no sample.
- **OpenAPI 3.1 `webhooks`:** rendered. The sidebar gets an `EVENT`-badged entry `Shipment status changed` below the tag groups (it sits outside the groups because the webhook has no `tags`), the page heading carries a `Webhook` chip, header parameters and the request body are shown, and the right panel says "Request samples: Payload" instead of "Response samples". One quirk: the webhook also shows `AUTHORIZATIONS: ApiKeyAuth`, because the document-level `security` requirement is applied to it. That is misleading for an outbound call; the fix is `security: []` on the webhook operation, which belongs in a copy of the spec, not in the shared one.

Gotchas: the built page depends on `cdn.redocly.com` at view time (see Expected output). Redoc renders `servers` as plain text, so the Prism mock URL in the spec is informational only; there is no console to point at it. And there is exactly one page: versions, changelogs, guides, and auth-gated access are all things you add around Redoc, not in it.
