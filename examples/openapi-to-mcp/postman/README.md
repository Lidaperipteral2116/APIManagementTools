# Postman: OpenAPI to collection to MCP server

**What this shows:** converting `specs/demo-api.yaml` into a Postman Collection v2.1 offline, running that collection against the Prism mock with newman, and then using Postman's hosted MCP Generator to turn the collection's requests into a downloadable Node.js MCP server.

Postman is best at the request-first workflow: if your team already lives in collections and environments, the MCP Generator lets you pick exactly the requests an agent should get, one tool per request, without writing a spec-to-tool config. It does not read OpenAPI directly; the spec becomes a collection first, and that conversion is where detail is lost (see Notes).

Everything up to the Postman UI runs offline and is captured below. The UI steps are a walkthrough with screenshot slots.

## Files

| File | What it is |
|---|---|
| `parcelio.postman_collection.json` | Generated by `openapi-to-postmanv2` 6.3.3 from the spec, untouched. 29 requests in 8 tag folders. |
| `parcelio.postman_environment.json` | Hand-written environment: `baseUrl` pointing at Prism, fake `apiKey` and `bearerToken`. |
| `add-oauth-token.js` | Optional post-processor that makes the 13 OAuth2 requests send `Authorization: Bearer {{bearerToken}}`. |
| `parcelio.with-token.postman_collection.json` | Output of the script above. |
| `images/` | Screenshot slots for the UI steps. |

## Prerequisites

- Node 22 (`npx` is enough; nothing is installed globally)
- Prism mock running. From the repo root:

```sh
npx -y @stoplight/prism-cli@5.16.0 mock -p 4010 specs/demo-api.yaml
```

## Part 1: spec to collection (offline)

Step 1. Convert the spec. Run from the repo root.

```sh
npx -y openapi-to-postmanv2@6.3.3 -s specs/demo-api.yaml \
  -o examples/openapi-to-mcp/postman/parcelio.postman_collection.json \
  -p -O folderStrategy=Tags
```

`-p` pretty-prints, `-O folderStrategy=Tags` groups requests by tag instead of by path segment (the CLI binary is `openapi2postmanv2`; `npx` resolves it from the package name).

Step 2. Look at what the converter did before trusting it. The collection carries the API-key scheme at collection level and an OAuth2 block on each write request:

```sh
node -e '
const c=require("./examples/openapi-to-mcp/postman/parcelio.postman_collection.json");
console.log(c.info.schema);
console.log(JSON.stringify(c.auth));
console.log(JSON.stringify(c.variable));'
```

Step 3. Run it against Prism with newman.

```sh
npx -y newman@6.2.2 run examples/openapi-to-mcp/postman/parcelio.postman_collection.json \
  -e examples/openapi-to-mcp/postman/parcelio.postman_environment.json
```

Step 4 (optional). Make the OAuth2 requests authenticate and run again.

```sh
node examples/openapi-to-mcp/postman/add-oauth-token.js \
  examples/openapi-to-mcp/postman/parcelio.postman_collection.json \
  examples/openapi-to-mcp/postman/parcelio.with-token.postman_collection.json
npx -y newman@6.2.2 run examples/openapi-to-mcp/postman/parcelio.with-token.postman_collection.json \
  -e examples/openapi-to-mcp/postman/parcelio.postman_environment.json
```

## Part 2: collection to MCP server (Postman web UI)

The MCP Generator lives in the Postman web app, not the desktop app or CLI. Steps 5 to 8 quote the labels from Postman's docs (fetched 2026-09-01); steps 9 onward are from the "Set up and start your generated MCP server locally" page.

Step 5. Import the collection. In Postman, use Import (top of the sidebar) and drop `parcelio.postman_collection.json` and `parcelio.postman_environment.json`. Alternatively import `specs/demo-api.yaml` directly; Postman runs the same converter and offers to create a collection. The import dialog has a View Import Settings link whose options, per the docs, "will vary depending on your specification"; the OpenAPI option set Postman documents includes "Folder organization" with "Paths" (default) or "Tags", the same choice openapi-to-postmanv2 calls `folderStrategy` (sources: https://learning.postman.com/docs/design-apis/specifications/import-a-specification and https://learning.postman.com/docs/design-apis/specifications/generate-collections, 2026-09-02). The exact label inside the import dialog was not checked in the UI.

Step 7. Pick requests. The documented flow searches public APIs on the Postman API Network, chooses a workspace, then: "Click through the workspace's collections and folders and select the requests you want to add to your MCP server. Click Add Requests." For Parcelio, add the whole Shipments, Packages, Tracking, Carriers, Rates and Addresses folders, and leave out `Ingest tracking event` (carrier-only endpoint) and the Webhooks folder unless the agent should manage subscriptions. Postman's docs describe only public workspaces at every step ("Choose one of the public workspaces", "add requests from other public workspaces") and say nothing about picking requests from a private workspace such as the one you imported into in step 5, so this walkthrough does not claim that works. If the picker does not show your workspace, the documented path is a public workspace (source: https://learning.postman.com/docs/postman-ai/mcp-servers/generate/, 2026-09-02).

Step 9. Run it locally. Requires "Node.js 18 or later". Unzip, then:

```sh
cd /path/to/your-mcp-server
npm install
npm run list-tools
```

Per the docs the layout is `mcpServer.js` (entry point), a `tools/` directory with one file per request, a `.env` file for secrets and a `README.md`. For each tool "open its tool file, and verify the baseUrl value is correct": the generated tools inherit whatever host the request had, so point them at `http://127.0.0.1:4010` for Prism. The `X-API-Key` header needs to be set the same way; the docs say to open the tool file and "use token to implement authentication", so expect a small edit per tool or a shared change in `lib/`. The README Postman writes into the ZIP says the `.env` holds one placeholder per source workspace, named after the workspace slug ("`ACME_API_KEY=`", "`WIDGETS_API_KEY=`"), read in tool files as `process.env.ACME_API_KEY`, and warns "This may not be correct for every API" (source: a server produced by the MCP Generator and pushed to GitHub unchanged enough to keep that README, https://github.com/ramborau/fb-messenger-mcp, checked 2026-09-02). So for Parcelio expect `<WORKSPACE_SLUG>_API_KEY`, and put the `X-API-Key` value there.

![step 9](images/step-9.png)
<!-- MAINTAINER: add screenshot of `npm run list-tools` output for the Parcelio server -->

Step 10. Start it. STDIO (what Claude Desktop uses):

```sh
node mcpServer.js
```

Streamable HTTP:

```sh
node mcpServer.js --streamable-http
```

Default port: the generated `mcpServer.js` listens on `process.env.PORT || 3001` and serves `/mcp`, and Postman's docs tell you to point the Postman MCP client at `http://localhost:3001/mcp`. There is no `--port` flag; the script only checks `process.argv` for `--streamable-http` and `--sse`. Set `PORT` in `.env` to change it (sources: https://learning.postman.com/docs/postman-ai/mcp-servers/interact and `mcpServer.js` in https://github.com/ramborau/fb-messenger-mcp, 2026-09-02).

Step 11. Connect Claude Desktop. Add to `claude_desktop_config.json` (macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "parcelio": {
      "command": "node",
      "args": ["/absolute/path/to/your-mcp-server/mcpServer.js"]
    }
  }
}
```

Restart Claude Desktop; the tools appear under the server name. Postman's own client can also talk to the server: create a new MCP request in Postman, choose STDIO and enter the command, or choose HTTP and enter the streamable-HTTP URL.

Why those codes:

- 401 on all 13 OAuth2 requests: the converter fills in the OAuth2 flow URLs and scopes but no access token, so newman sends no `Authorization` header and Prism rejects the request. Prism does not check the API key on these because the operation's security override replaces the global `X-API-Key` requirement.
- 422 on `List shipments`, `List carriers`, `Quote rates`, `Validate an address`: the converter's placeholder values (`<dateTime>`, `<boolean>`, `"country": "<string>"` where a 2-letter code is required) fail Prism's request validation. That is the converter being literal, not the spec being wrong.
- 200 on the rest: path parameters got generated values matching the spec's `pattern` (for example `shp_SBWm4xlj`), and `cursor=<string>` is a valid string.

newman exits 0 because the collection has no test scripts; a 4xx is not a failure unless you assert on it.

Step 4 (newman, after `add-oauth-token.js`): `patched 13 oauth2 requests`. 29 requests: 14 x 200, 1 x 201, 4 x 204, 10 x 422. ## Notes

What worked cleanly:

- The converter handled the OpenAPI 3.1 spec (`type: [string, 'null']`, `examples` arrays, `const`) without complaint and produced a valid v2.1 collection in one pass. All 29 operations are present, grouped by tag, each with saved example responses for every documented status code (this is why the file is 470 KB).
- Path parameters get values that satisfy the spec's regex patterns, so Prism accepts them without editing.
- Collection-level auth correctly became `apikey` in header `X-API-Key` with value `{{apiKey}}`, and the `Idempotency-Key` header on `Create a shipment` survived.

What was lost or changed in the OpenAPI to collection conversion (checked in the JSON, not assumed):

- Security scheme semantics. Each OAuth2 request gets `authUrl`, `accessTokenUrl`, `grant_type: authorization_code` and one `scope` string that is the union of all four scopes in `components.securitySchemes` (`shipments:read shipments:write tracking:write webhooks:manage`). The per-operation scope (for example `createShipment` needs only `shipments:write`, `createWebhookSubscription` only `webhooks:manage`) is gone. `redirect_uri` is set to the token URL, which is wrong for any real flow. No token is stored, so the requests cannot run unattended; `add-oauth-token.js` shows the two keys (`accessToken`, `addTokenTo`) that fix that.
- Cursor pagination became two ordinary query params, `limit=20` and `cursor=<string>`, both enabled. Nothing links `next_cursor` in the response to `cursor` in the next request; an MCP tool generated from this request will have a `cursor` string argument and no idea what to put in it unless the description says so. The `Limit` description text survived, so the agent at least sees "Maximum number of items to return per page."
- The multipart upload (`Upload a shipment document`) became a `formdata` body where `file` is `"type": "text"` with value `<string>`, not a file field. The `contentType` hint (`application/pdf, image/png, image/jpeg`) is kept as metadata. Postman can send it, but as a text part; an agent tool built from it would post a string, not bytes.
- The binary label endpoint kept only the first content type as `Accept: application/pdf`; the `image/png` alternative exists only as a saved example response.
- The `shipmentStatusChanged` webhook (an OpenAPI `webhooks` entry, not a path) is not in the collection at all.
- Two of the spec's deliberate defects show up as names: `listPackages` has no `summary`, so the request is called `list Packages` (derived from the path); `tracking_event_ingest` has a summary, so its operationId casing is invisible here. Missing descriptions on `dispatchShipment`, `removePackage`, `cancelPickup` and `testWebhookSubscription` are simply empty in the collection, and will be empty tool descriptions after generation unless you edit the request descriptions in Postman first.
- Placeholder values (`<string>`, `<dateTime>`, `<boolean>`) are literal strings. They are fine as documentation and wrong as requests.

MCP Generator specifics:

- It builds "for each request" one tool, from the request's name, description, params and body. The quality of a tool is the quality of the Postman request, so fix names and descriptions in Postman before generating.
- Transports: STDIO and streamable HTTP, chosen at start time with `--streamable-http`.
- The documented picker browses "public APIs from the Postman API Network" and every step of the docs says "public workspaces"; selecting requests from a private workspace is not documented.
- Account: a Postman account is needed for the web UI. Neither the MCP Generator docs nor the pricing page states a plan restriction or a per-server request limit for the generator; the pricing page mentions MCP only as the "MCP Client" and "MCP Server Catalog" line items (https://www.postman.com/pricing, 2026-09-02).

Pinned versions: `openapi-to-postmanv2@6.3.3`, `newman@6.2.2`, `@stoplight/prism-cli@5.16.0`.
